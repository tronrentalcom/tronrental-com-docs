## वेबहुक

आपके खाते का **एक ही वेबहुक URL** होता है और सभी घटनाएँ वहीं भेजी जाती हैं। इसे [Dashboard → API](https://tronrental.com/dashboard/api) में या [वेबहुक कॉन्फ़िगर करें](/hi/api-reference/webhooks/configure) से सेट करें।

### घटनाएँ

आज दस घटनाएँ मौजूद हैं।

| घटना | कब भेजी जाती है |
|-------|-----------|
| `order.updated` | आपके खाते के एनर्जी या बैंडविड्थ ऑर्डर की स्थिति बदली — ऑर्डर चाहे जहाँ से दिया गया हो: API, वेबसाइट, Telegram बॉट या ऑटो रिफिल |
| `activation.updated` | आपके बैलेंस से भुगतान किया गया एड्रेस सक्रियण पूरा हुआ |
| `withdrawal.completed` | आपके बैलेंस से निकासी भेज दी गई |
| `withdrawal.failed` | निकासी अस्वीकार हुई और राशि आपके बैलेंस में लौट गई |
| `invoice.updated` | आपके खाते के इनवॉइस की स्थिति बदली |
| `subscription.transfer` | Smart Mode ने किसी निगरानी वाले पते से हुए ट्रांसफ़र का भुगतान किया |
| `package.transfer` | Transfer Package ने अपने पते से हुए ट्रांसफ़र का भुगतान किया |
| `package.completed` | Transfer Package ने ट्रांसफ़र की सेवा बंद कर दी |
| `package.activated` | Transfer Package सक्रिय हुआ |
| `package.expired` | बिना भुगतान वाले Transfer Package इनवॉइस की अवधि समाप्त हुई |

<Note>
  3 नवंबर 2026 से `order.updated` **खाते के हर ऑर्डर** के लिए भेजा जाता है; पहले यह केवल API कुंजी से बनाए गए ऑर्डर के लिए भेजा जाता था। चैनल `source` फ़ील्ड से पहचानें। [बैंडविड्थ रेंटल](/hi/api-reference/bandwidth-rentals/create-rental) घटनाएँ नहीं भेजते।
</Note>

### लिफ़ाफ़ा

हर डिलीवरी में वही तीन शीर्ष-स्तरीय कुंजियाँ होती हैं। `timestamp` वह क्षण है जब हमने घटना बनाई — ISO-8601, UTC में।

```json Response
{
  "event": "order.updated",
  "data": { },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

हेडर:

| हेडर | मान |
|--------|-------|
| `Content-Type` | `application/json` |
| `X-Webhook-Signature` | `sha256=<hex>` — नीचे «हस्ताक्षर की जाँच» देखें |
| `Host` | आपके URL का होस्ट |

### `order.updated`

<ResponseField name="id" type="number">
  ऑर्डर ID।
</ResponseField>

<ResponseField name="type" type="string">
  `energy` या `bandwidth`।
</ResponseField>

<ResponseField name="status" type="string">
  `processing`, `filled`, `partial`, `failed`, `reclaimed` या `reclaim_failed`। **यही फ़ील्ड सत्य का स्रोत है** — नीचे दी चेतावनी देखें।
</ResponseField>

<ResponseField name="source" type="string">
  ऑर्डर कहाँ से दिया गया: `api`, `web` (वेबसाइट), `bot` (Telegram बॉट), `autorefill` ([ऑटो रिफिल](/hi/api-reference/auto-refill/overview) नियम), `faucet` (मुफ़्त बैंडविड्थ) या `broadcast` (Energy Broadcast)।
</ResponseField>

<ResponseField name="target_address" type="string">
  वह पता जिसे संसाधन डेलिगेट किया गया।
</ResponseField>

<ResponseField name="volume" type="number">
  ऑर्डर की गई मात्रा — एनर्जी यूनिट या बैंडविड्थ पॉइंट।
</ResponseField>

<ResponseField name="expected_volume" type="number">
  `volume` जैसा ही। यह इसलिए है कि अपेक्षित और वितरित की तुलना बिना यह जाने की जा सके कि कौन-सा फ़ील्ड क्या दर्शाता है।
</ResponseField>

<ResponseField name="delivered_volume" type="number">
  अब तक वास्तव में कितना डेलिगेट हुआ। ऑर्डर `filled` होने पर `volume` के बराबर; `processing` और `partial` में अब तक दिए गए हिस्सों का योग; विफलता पर `0`।
</ResponseField>

<ResponseField name="price_trx" type="string">
  ऑर्डर की कीमत TRX में, दशमलव स्ट्रिंग के रूप में।
</ResponseField>

<ResponseField name="delegate_txid" type="string | null">
  वह लेनदेन जिसने संसाधन डेलिगेट किया।
</ResponseField>

<ResponseField name="undelegate_txid" type="string | null">
  वह लेनदेन जिसने किराया समाप्त होने पर उसे वापस लिया।
</ResponseField>

<ResponseField name="reclaim_at" type="string | null">
  संसाधन कब वापस लिया जाना है, ISO-8601; टाइमर से वापस न लिए जाने वाले ऑर्डर में `null`।
</ResponseField>

```json Response
{
  "event": "order.updated",
  "data": {
    "id": 247033,
    "type": "energy",
    "status": "filled",
    "source": "web",
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "volume": 65000,
    "expected_volume": 65000,
    "delivered_volume": 65000,
    "price_trx": "2.75",
    "delegate_txid": "a1b2c3d4e5f6...",
    "undelegate_txid": null,
    "reclaim_at": "2026-09-15T07:44:56+00:00"
  },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

<Warning>
**परिणाम `status` से आँकें, `delegate_txid` की मौजूदगी से नहीं।** विफल ऑर्डर में भी लेनदेन ID हो सकता है — हम उसे जानबूझकर रखते हैं ताकि विफलता की जाँच हो सके। संसाधन मिला या नहीं, यह केवल `status` बताता है।
</Warning>

बड़े ऑर्डर को हम भीतर हिस्सों में बाँटते हैं, पर वह हमारा काम है: आपको **प्रति ऑर्डर एक ही वेबहुक** मिलता है, प्रति हिस्सा नहीं।

एक ही ऑर्डर के लिए वही `status` एक से अधिक बार आ सकता है। `(id, status)` को कुंजी मानें और दोहराव को अनदेखा करें।

### `activation.updated`

तब भेजा जाता है जब आपके बैलेंस से भुगतान किया गया सक्रियण पूरा होता है: [एड्रेस सक्रिय करें](/hi/api-reference/energy/activate-address) से, वेबसाइट पर, या अपने-आप तब, जब किसी ऑर्डर या Transfer Package को निष्क्रिय एड्रेस सक्रिय करना हो।

<ResponseField name="id" type="number">
  सक्रियण रिकॉर्ड की ID — वही `id` जो एड्रेस सक्रिय करें लौटाता है।
</ResponseField>

<ResponseField name="target_address" type="string">
  वह एड्रेस जिसे सक्रिय किया गया।
</ResponseField>

<ResponseField name="status" type="string">
  `completed` — हमने सक्रियण नेटवर्क पर भेज दिया; `already_activated` — एड्रेस पहले से सक्रिय था और कुछ नहीं काटा गया; `failed` — सक्रियण नहीं हुआ और कटौती लौटा दी गई; `pending` — लेनदेन भेजा गया, पर उसका परिणाम अभी पता नहीं है, इसलिए हमारी जाँच तक कटौती रोकी गई है।
</ResponseField>

<ResponseField name="txid" type="string | null">
  सक्रियण लेनदेन, या कोई न हो तो `null`।
</ResponseField>

<ResponseField name="cost_trx" type="string">
  अंत में सक्रियण की आपकी लागत, दशमलव स्ट्रिंग के रूप में: रिफ़ंड के बाद और पहले से सक्रिय एड्रेस के लिए `0`।
</ResponseField>

```json Response
{
  "event": "activation.updated",
  "data": {
    "id": 12345,
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "txid": "a1b2c3d4e5f6...",
    "cost_trx": "1.2"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Note>
  `pending` दुर्लभ है, और आज उसका अंतिम परिणाम दूसरी घटना नहीं भेजता। अगर कोई सक्रियण `pending` में ही रहे, तो सपोर्ट से संपर्क करें।
</Note>

### `withdrawal.completed` और `withdrawal.failed`

आपके बैलेंस से निकासी का परिणाम आने पर भेजे जाते हैं, चाहे अनुरोध कैसे भी किया गया हो: [निकासी बनाएं](/hi/api-reference/account/withdrawals), वेबसाइट या Telegram बॉट। `withdrawal.completed` — लेनदेन TRON नेटवर्क पर भेज दिया गया; `withdrawal.failed` — निकासी अस्वीकार हुई और `total_trx` आपके बैलेंस में लौटा दिया गया।

<ResponseField name="id" type="number">
  निकासी ID — वही `id` जो निकासी बनाएं लौटाता है।
</ResponseField>

<ResponseField name="status" type="string">
  `completed` या `failed` — इवेंट के नाम जैसा ही।
</ResponseField>

<ResponseField name="currency" type="string">
  `TRX` या `USDT`।
</ResponseField>

<ResponseField name="to_address" type="string">
  प्राप्तकर्ता का पता।
</ResponseField>

<ResponseField name="amount_trx" type="string">
  भेजी गई राशि TRX में, दशमलव स्ट्रिंग के रूप में। USDT निकासी में — काटा गया उसका TRX समतुल्य।
</ResponseField>

<ResponseField name="fee_trx" type="string">
  शुल्क TRX में।
</ResponseField>

<ResponseField name="total_trx" type="string">
  बैलेंस से काटी गई राशि: `amount_trx` + `fee_trx`।
</ResponseField>

<ResponseField name="amount_usdt" type="string | null">
  USDT निकासी में भेजी गई USDT राशि; अन्यथा `null`।
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  `withdrawal.completed` में लेनदेन; `withdrawal.failed` में `null`।
</ResponseField>

<ResponseField name="refunded_trx" type="string | null">
  `withdrawal.failed` में बैलेंस में लौटाई गई राशि (`total_trx`); `withdrawal.completed` में `null`।
</ResponseField>

<ResponseField name="created_at" type="string">
  निकासी का अनुरोध कब हुआ, ISO-8601 UTC।
</ResponseField>

```json Response
{
  "event": "withdrawal.completed",
  "data": {
    "id": 4821,
    "status": "completed",
    "currency": "TRX",
    "to_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "amount_trx": "250",
    "fee_trx": "1",
    "total_trx": "251",
    "amount_usdt": null,
    "tx_hash": "a1b2c3d4e5f6...",
    "refunded_trx": null,
    "created_at": "2026-11-13T09:12:44.118203+00:00"
  },
  "timestamp": "2026-11-13T09:13:05.402911+00:00"
}
```

<Note>
  कभी-कभी निकासी `pending` में रुकती है जब तक हम उसकी जाँच करते हैं। इस पर कोई इवेंट नहीं आता — परिणाम पर आता है। मौजूदा स्थिति देखने के लिए निकासी को [निकासी सूची](/hi/api-reference/account/withdrawals) से पढ़ें।
</Note>

### `invoice.updated`

इनवॉइस की स्थिति बदलने पर उस खाते को भेजा जाता है जिसका वह इनवॉइस है। `data` वही ऑब्जेक्ट है जो [इनवॉइस प्राप्त करें](/hi/api-reference/invoices/get-invoice) लौटाता है, दो अंतरों के साथ: `error_message` हमेशा `null` होता है, और `status` वह स्थिति है जिसकी सूचना यह घटना देती है।

| `status` | अर्थ |
|----------|---------|
| `paid` | भुगतान मिला, डिलीवरी जारी है |
| `underpaid` | कीमत से कम राशि आई; बाकी राशि कब तक भेजी जा सकती है, यह `topup_until` बताता है |
| `delegated` | संसाधन डेलिगेट हो गया |
| `failed` | डिलीवरी विफल रही |
| `expired` | इनवॉइस की अवधि खत्म होने से पहले भुगतान नहीं आया |
| `reclaimed` | रेंटल खत्म हुआ और संसाधन वापस ले लिया गया |
| `reclaim_failed` | संसाधन वापस नहीं लिया जा सका |

```json Response
{
  "event": "invoice.updated",
  "data": {
    "invoice_id": "7c1f0c2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
    "payment_address": "TPaymentAddress...",
    "target_address": "TRecipientAddress...",
    "energy_amount": 65000,
    "duration": "1h",
    "price_trx": "2.75",
    "price_usdt": "0.64",
    "status": "delegated",
    "error_message": null,
    "tx_hash": "a1b2c3d4e5f6...",
    "paid_at": "2026-11-03T14:50:40+00:00",
    "completed_at": "2026-11-03T14:51:16+00:00",
    "expires_at": "2026-11-03T15:20:00+00:00",
    "created_at": "2026-11-03T14:50:00+00:00"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Warning>
  **स्थिति दोहराई जा सकती है, और घटनाएँ क्रम से बाहर आ सकती हैं** — `delegated` अपने से पहले वाले `paid` से पहले आ सकता है। जब सटीक स्थिति मायने रखती हो, तो [इनवॉइस प्राप्त करें](/hi/api-reference/invoices/get-invoice) से पुष्टि करें।
</Warning>

इनवॉइस आपके खाते का होता है, अगर आपने उसे वेबसाइट पर साइन इन करके बनाया हो। बिना साइन इन के बनाए गए इनवॉइस का कोई मालिक नहीं होता और वह घटनाएँ नहीं भेजता — और आज इसमें API कुंजी से बनाया गया इनवॉइस भी शामिल है।

### Transfer Package घटनाएँ

चारों `package.*` घटनाएँ उस खाते को जाती हैं जो **पैकेज का मालिक** है। साइन इन किए बिना या API कुंजी के बिना इनवॉइस से खरीदे गए पैकेज का कोई मालिक नहीं होता, और उससे कोई घटना नहीं बनती। रद्द किए गए इनवॉइस, अस्वीकृत खरीद और मैन्युअल समीक्षा में रुकी खरीद से भी कोई घटना नहीं बनती; समीक्षा वाला पैकेज सक्रिय होने पर `package.activated` भेजता है।

हर `package.*` घटना के `data` में ये फ़ील्ड होते हैं:

<ResponseField name="package_id" type="number">
  पैकेज ID — [पैकेज सूची](/hi/api-reference/transfer-packages/list) में `id`।
</ResponseField>

<ResponseField name="address" type="string">
  वह पता जिसकी सेवा पैकेज करता है।
</ResponseField>

<ResponseField name="status" type="string">
  घटना के बाद पैकेज की स्थिति: `package.transfer` के लिए `active` या `completed`, `package.completed` के लिए `completed`, `package.activated` के लिए `active`, `package.expired` के लिए `expired`।
</ResponseField>

<ResponseField name="quota_total" type="number">
  पैकेज कितने ट्रांसफ़र के साथ खरीदा गया था।
</ResponseField>

<ResponseField name="remaining" type="number">
  घटना जिस बदलाव की सूचना देती है, उसके बाद इस पैकेज में बचे ट्रांसफ़र — एक निरपेक्ष संख्या, अंतर नहीं।
</ResponseField>

<Warning>
  **घटनाएँ क्रम से बाहर आ सकती हैं।** हर घटना अलग से भेजी जाती है और लगभग 35 सेकंड तक दोबारा कोशिश होती है, इसलिए किसी ट्रांसफ़र से हुई `package.completed` उसी ट्रांसफ़र की `package.transfer` से पहले आ सकती है, और `package.transfer` `package.activated` से पहले आ सकती है। हर `package_id` के लिए अब तक देखा गया **सबसे कम** `remaining` रखें: यह कभी नहीं बढ़ता। `completed` और `expired` अंतिम हैं।
</Warning>

<Note>
  `remaining` बिना किसी घटना के भी घट सकता है। कई ट्रांसफ़र वाला पैकेज दैनिक सदस्यता के रूप में दिन में एक ट्रांसफ़र लेता है — पहला सक्रिय होते समय, इसीलिए 500 ट्रांसफ़र वाला पैकेज `remaining: 499` से शुरू होता है — और इस कटौती की अलग सूचना नहीं आती। एक ही पते से एक ही ब्लॉक में हुए दो ट्रांसफ़र एक जैसा `remaining` बता सकते हैं। `remaining` को संकेत मानें और [पैकेज सूची](/hi/api-reference/transfer-packages/list) को सच्चाई का स्रोत।
</Note>

दोबारा भेजी गई घटना पहचानने के लिए `package.transfer` में `(package_id, tx_hash)` और बाकी में `(event, package_id)` का उपयोग करें: दोबारा भेजी गई घटना में वही बॉडी, वही `timestamp` और वही हस्ताक्षर होते हैं।

#### `package.transfer`

पते से हुए ट्रांसफ़र का भुगतान पैकेज से हुआ। ट्रांसफ़र जिस **हर पैकेज** से काटा गया, उसके लिए एक बार भेजी जाती है — लगभग हमेशा प्रति ट्रांसफ़र एक घटना; जो ट्रांसफ़र एक पैकेज का आख़िरी ट्रांसफ़र लेकर अगले पैकेज पर जारी रहता है, वह दोनों के लिए एक-एक घटना देता है।

<ResponseField name="tx_hash" type="string">
  चेन पर ट्रांसफ़र का ट्रांज़ैक्शन।
</ResponseField>

<ResponseField name="units" type="number">
  इस ट्रांज़ैक्शन के लिए **इस** पैकेज से काटे गए ट्रांसफ़र। ऐसे पते पर ट्रांसफ़र जिसके पास USDT नहीं है, दोगुनी ऊर्जा लेता है और `2` गिना जाता है, जो दो पैकेजों में बँट सकता है।
</ResponseField>

यहाँ अगर इस ट्रांसफ़र ने पैकेज खत्म कर दिया तो `status` `completed` होता है।

```json Response
{
  "event": "package.transfer",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 312,
    "tx_hash": "9f8e7d6c5b4a...",
    "units": 1
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.completed`

पैकेज ने ट्रांसफ़र की सेवा बंद कर दी।

<ResponseField name="reason" type="string">
  `transfer` — एक ट्रांसफ़र ने पैकेज खत्म किया; `subscription` — दैनिक कटौती ने उसे खत्म किया; `manual` — सपोर्ट ने पैकेज बंद किया। `manual` के बाद `remaining` शून्य से अधिक हो सकता है, लेकिन वे ट्रांसफ़र अब उपयोग नहीं किए जा सकते।
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  `reason: "transfer"` होने पर वह ट्रांसफ़र जिसने पैकेज बंद किया; अन्यथा `null`।
</ResponseField>

बिना शेष वाला पैकेज — जैसे एक ट्रांसफ़र वाला सामान्य पैकेज, जिसकी पहली दैनिक कटौती ने उसका इकलौता ट्रांसफ़र ले लिया — अगले ट्रांसफ़र से अपनी `package.transfer` के बिना बंद हो जाता है: आपको उस ट्रांसफ़र के `tx_hash` के साथ केवल `package.completed` मिलती है।

```json Response
{
  "event": "package.completed",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "quota_total": 500,
    "remaining": 0,

    "tx_hash": "9f8e7d6c5b4a..."
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

### डिलीवरी

- अधिकतम **3 प्रयास**, बीच में **1 सेकंड** और फिर **4 सेकंड** का ठहराव। सफलता के बाद और अंतिम प्रयास के बाद कोई ठहराव नहीं।
- प्रति प्रयास **10 सेकंड** का टाइमआउट।
- हम कोई भी **`2xx`** स्वीकार करते हैं। बाकी सब विफल प्रयास गिना जाता है।
- **रीडायरेक्ट का पालन नहीं किया जाता।** `301`/`302` एक विफल प्रयास है, छलाँग नहीं।
- छूटी हुई घटनाएँ बाद में **दोबारा नहीं भेजी जातीं**। तीनों प्रयास विफल हुए तो वह घटना चली गई; दोबारा भेजे जाने की प्रतीक्षा के बजाय [ऑर्डर देखें](/hi/api-reference/orders/get-order), [इनवॉइस प्राप्त करें](/hi/api-reference/invoices/get-invoice) या [पैकेज सूची](/hi/api-reference/transfer-packages/list) से मिलान करें।
- **घटनाओं का क्रम तय नहीं है।** हर घटना अलग से डिलीवर होती है, इसलिए बाद वाली घटना पहले आ सकती है। दोबारा प्रयास में वही बॉडी, वही `timestamp` और वही हस्ताक्षर होते हैं।
- खाते का हर ऑर्डर घटनाएँ भेजता है, ऑटो रिफिल भी, इसलिए व्यस्त खाते को बहुत सारी घटनाएँ मिलती हैं। तुरंत `2xx` लौटाएँ और भारी काम जवाब देने के बाद करें।

आपका URL किसी **सार्वजनिक** पते पर रिज़ॉल्व होना चाहिए। लूपबैक, निजी और लिंक-लोकल रेंज अस्वीकार की जाती हैं, और वह होस्ट भी जो रिज़ॉल्व ही न हो — दोनों स्थितियों में कुछ नहीं भेजा जाता और लॉग में कोई पंक्ति नहीं लिखी जाती।

### हस्ताक्षर की जाँच

हर अनुरोध में `X-Webhook-Signature: sha256=<hex>` होता है — आपके वेबहुक सीक्रेट से, **कच्चे अनुरोध बॉडी** पर निकाला गया HMAC-SHA256।

आपकी जाँच चलेगी या नहीं, यह दो बातों पर निर्भर है:

1. तुलना से पहले **`sha256=` उपसर्ग हटाएँ**। हेडर केवल हेक्स डाइजेस्ट नहीं है।
2. **प्राप्त बाइट्स का हैश लें**, दोबारा सीरियलाइज़ किए गए ऑब्जेक्ट का नहीं। JSON को पार्स करके फिर से लिखने पर कुंजियों का क्रम और स्पेस बदल जाते हैं, और हस्ताक्षर कभी नहीं मिलेगा।

आपका साइनिंग सीक्रेट [Dashboard → API](https://tronrental.com/dashboard/api) में वेबहुक URL के बगल में दिखता है। API कुंजी वाले अनुरोधों को यह नहीं लौटाया जाता — पढ़ने के लिए वेबसाइट पर साइन इन करना होगा।

<CodeGroup>
```python Python
import hashlib
import hmac

def verify_webhook(raw_body: bytes, signature_header: str, secret: str) -> bool:
    prefix, _, received = signature_header.partition("=")
    if prefix != "sha256" or not received:
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received)
```

```javascript JavaScript
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const [prefix, received] = String(signatureHeader).split("=");
  if (prefix !== "sha256" || !received) return false;
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```
</CodeGroup>

<Warning>
  सामग्री पर कार्रवाई करने से पहले हस्ताक्षर जाँचें, और स्थिर समय में तुलना करें (`hmac.compare_digest` / `crypto.timingSafeEqual`)। `==` से तुलना समय के ज़रिए जानकारी लीक करती है।
</Warning>
