## Webhooks

Su cuenta tiene **una sola URL de webhook** y todos los eventos se envían a ella. Configúrela en [Dashboard → API](https://tronrental.com/dashboard/api) o mediante [Configurar webhook](/es/api-reference/webhooks/configure).

### Eventos

Hoy existen diez eventos.

| Evento | Cuándo se envía |
|-------|-----------|
| `order.updated` | Un pedido de energía o ancho de banda de su cuenta cambia de estado, sin importar cómo se hizo: API, sitio web, bot de Telegram o recarga automática |
| `activation.updated` | Se resolvió una activación de dirección pagada con su saldo |
| `withdrawal.completed` | Se envió un retiro de su saldo |
| `withdrawal.failed` | Se rechazó un retiro y su importe volvió a su saldo |
| `invoice.updated` | Una factura de su cuenta cambia de estado |
| `subscription.transfer` | Smart Mode pagó una transferencia de una dirección vigilada |
| `package.transfer` | Un Transfer Package pagó una transferencia desde su dirección |
| `package.completed` | Un Transfer Package dejó de cubrir transferencias |
| `package.activated` | Un Transfer Package se activó |
| `package.expired` | Venció la factura sin pagar de un Transfer Package |

<Note>
  Desde el 3 de noviembre de 2026, `order.updated` cubre **todos los pedidos de la cuenta**; antes solo se enviaba para pedidos creados con una clave API. Distinga los canales por el campo `source`. Los [alquileres de ancho de banda](/es/api-reference/bandwidth-rentals/create-rental) no envían eventos.
</Note>

### Sobre del mensaje

Cada entrega tiene las mismas tres claves de nivel superior. `timestamp` es el momento en que compusimos el evento, ISO-8601 en UTC.

```json Response
{
  "event": "order.updated",
  "data": { },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

Cabeceras:

| Cabecera | Valor |
|--------|-------|
| `Content-Type` | `application/json` |
| `X-Webhook-Signature` | `sha256=<hex>` — vea la sección «Verificación de la firma» más abajo |
| `Host` | el host de su URL |

### `order.updated`

<ResponseField name="id" type="number">
  ID del pedido.
</ResponseField>

<ResponseField name="type" type="string">
  `energy` o `bandwidth`.
</ResponseField>

<ResponseField name="status" type="string">
  `processing`, `filled`, `partial`, `failed`, `reclaimed` o `reclaim_failed`. **Este campo es la fuente de verdad**; vea la advertencia siguiente.
</ResponseField>

<ResponseField name="source" type="string">
  Dónde se hizo el pedido: `api`, `web` (el sitio web), `bot` (el bot de Telegram), `autorefill` (una regla de [Recarga automática](/es/api-reference/auto-refill/overview)), `faucet` (ancho de banda gratuito) o `broadcast` (Energy Broadcast).
</ResponseField>

<ResponseField name="target_address" type="string">
  Dirección a la que se delegó el recurso.
</ResponseField>

<ResponseField name="volume" type="number">
  Cantidad pedida: unidades de energía o puntos de bandwidth.
</ResponseField>

<ResponseField name="expected_volume" type="number">
  Igual que `volume`. Está presente para poder comparar lo esperado con lo entregado sin averiguar qué significa cada campo.
</ResponseField>

<ResponseField name="delivered_volume" type="number">
  Cuánto se ha delegado realmente hasta ahora. Igual a `volume` cuando el pedido está `filled`; en `processing` y `partial` es la suma de las partes ya entregadas, y `0` si falló.
</ResponseField>

<ResponseField name="price_trx" type="string">
  Precio del pedido en TRX, como cadena decimal.
</ResponseField>

<ResponseField name="delegate_txid" type="string | null">
  Transacción que delegó el recurso.
</ResponseField>

<ResponseField name="undelegate_txid" type="string | null">
  Transacción que lo recuperó al terminar el alquiler.
</ResponseField>

<ResponseField name="reclaim_at" type="string | null">
  Cuándo está previsto recuperar el recurso, ISO-8601, o `null` en los pedidos que no se recuperan por temporizador.
</ResponseField>

```json Response
{
  "event": "order.updated",
  "data": {
    "id": 247033,
    "type": "energy",
    "status": "filled",
    "source": "web",
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "volume": 65000,
    "expected_volume": 65000,
    "delivered_volume": 65000,
    "price_trx": "2.75",
    "delegate_txid": "a1b2c3d4e5f6...",
    "undelegate_txid": null,
    "reclaim_at": "2026-09-15T07:44:56+00:00"
  },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

<Warning>
**Juzgue el resultado por `status`, nunca por la presencia de `delegate_txid`.** Un pedido fallido también puede llevar un identificador de transacción: lo conservamos a propósito para poder investigar el fallo. Solo `status` dice si recibió el recurso.
</Warning>

Internamente dividimos los pedidos grandes en partes, pero eso es asunto nuestro: usted recibe **un webhook por pedido**, nunca uno por parte.

El mismo `status` puede llegar más de una vez para un pedido. Use `(id, status)` como clave e ignore la repetición.

### `activation.updated`

Se envía cuando se resuelve una activación pagada con su saldo: una hecha con [Activar direccion](/es/api-reference/energy/activate-address), en el sitio web o automáticamente cuando un pedido o un Transfer Package necesita activar una dirección inactiva.

<ResponseField name="id" type="number">
  ID del registro de activación: el `id` que devuelve Activar direccion.
</ResponseField>

<ResponseField name="target_address" type="string">
  La dirección que se activó.
</ResponseField>

<ResponseField name="status" type="string">
  `completed`: enviamos la activación a la red; `already_activated`: la dirección ya estaba activa y no se cobró nada; `failed`: la activación no se realizó y el cargo se reembolsó; `pending`: la transacción se envió, pero su resultado aún no se conoce, así que el cargo queda retenido hasta que lo comprobemos.
</ResponseField>

<ResponseField name="txid" type="string | null">
  La transacción de activación, o `null` si no la hay.
</ResponseField>

<ResponseField name="cost_trx" type="string">
  Lo que finalmente le costó la activación, como cadena decimal: `0` tras un reembolso y para una dirección que ya estaba activa.
</ResponseField>

```json Response
{
  "event": "activation.updated",
  "data": {
    "id": 12345,
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "txid": "a1b2c3d4e5f6...",
    "cost_trx": "1.2"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Note>
  `pending` es poco frecuente, y hoy su resultado final no envía un segundo evento. Si una activación se queda en `pending`, contacte con soporte.
</Note>

### `withdrawal.completed` y `withdrawal.failed`

Se envían cuando un retiro de su saldo tiene resultado, sin importar cómo se solicitó: [Crear retiro](/es/api-reference/account/withdrawals), el sitio web o el bot de Telegram. `withdrawal.completed`: la transacción se envió a la red TRON; `withdrawal.failed`: el retiro se rechazó y `total_trx` volvió a su saldo.

<ResponseField name="id" type="number">
  ID del retiro: el `id` que devuelve Crear retiro.
</ResponseField>

<ResponseField name="status" type="string">
  `completed` o `failed`, igual que el nombre del evento.
</ResponseField>

<ResponseField name="currency" type="string">
  `TRX` o `USDT`.
</ResponseField>

<ResponseField name="to_address" type="string">
  La dirección de destino.
</ResponseField>

<ResponseField name="amount_trx" type="string">
  El importe enviado en TRX, como cadena decimal. En un retiro de USDT, su equivalente en TRX que se cobró.
</ResponseField>

<ResponseField name="fee_trx" type="string">
  La comisión en TRX.
</ResponseField>

<ResponseField name="total_trx" type="string">
  Lo cobrado de su saldo: `amount_trx` + `fee_trx`.
</ResponseField>

<ResponseField name="amount_usdt" type="string | null">
  El importe en USDT enviado en un retiro de USDT; si no, `null`.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  La transacción en `withdrawal.completed`; `null` en `withdrawal.failed`.
</ResponseField>

<ResponseField name="refunded_trx" type="string | null">
  Lo devuelto a su saldo en `withdrawal.failed` (`total_trx`); `null` en `withdrawal.completed`.
</ResponseField>

<ResponseField name="created_at" type="string">
  Cuándo se solicitó el retiro, ISO-8601 UTC.
</ResponseField>

```json Response
{
  "event": "withdrawal.completed",
  "data": {
    "id": 4821,
    "status": "completed",
    "currency": "TRX",
    "to_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "amount_trx": "250",
    "fee_trx": "1",
    "total_trx": "251",
    "amount_usdt": null,
    "tx_hash": "a1b2c3d4e5f6...",
    "refunded_trx": null,
    "created_at": "2026-11-13T09:12:44.118203+00:00"
  },
  "timestamp": "2026-11-13T09:13:05.402911+00:00"
}
```

<Note>
  A veces un retiro espera en `pending` mientras lo revisamos. Eso no envía evento; su resultado sí. Para ver el estado actual, consulte el retiro con [Listar retiros](/es/api-reference/account/withdrawals).
</Note>

### `invoice.updated`

Se envía a la cuenta propietaria de la factura cuando cambia su estado. `data` es el objeto que devuelve [Obtener factura](/es/api-reference/invoices/get-invoice), con dos diferencias: `error_message` siempre es `null`, y `status` es el estado que anuncia este evento.

| `status` | Significado |
|----------|---------|
| `paid` | Pago recibido, entrega en curso |
| `underpaid` | Llegó menos que el precio; `topup_until` indica hasta cuándo se puede enviar el resto |
| `delegated` | El recurso se delegó |
| `failed` | La entrega falló |
| `expired` | No llegó ningún pago antes de que venciera la factura |
| `reclaimed` | El alquiler terminó y el recurso se retiró |
| `reclaim_failed` | No se pudo retirar el recurso |

```json Response
{
  "event": "invoice.updated",
  "data": {
    "invoice_id": "7c1f0c2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
    "payment_address": "TPaymentAddress...",
    "target_address": "TRecipientAddress...",
    "energy_amount": 65000,
    "duration": "1h",
    "price_trx": "2.75",
    "price_usdt": "0.64",
    "status": "delegated",
    "error_message": null,
    "tx_hash": "a1b2c3d4e5f6...",
    "paid_at": "2026-11-03T14:50:40+00:00",
    "completed_at": "2026-11-03T14:51:16+00:00",
    "expires_at": "2026-11-03T15:20:00+00:00",
    "created_at": "2026-11-03T14:50:00+00:00"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Warning>
  **Un estado puede repetirse y los eventos pueden llegar desordenados**: un `delegated` puede llegar antes que el `paid` que lo precedió. Cuando importe el estado exacto, confírmelo con [Obtener factura](/es/api-reference/invoices/get-invoice).
</Warning>

Una factura pertenece a su cuenta cuando la creó con la sesión iniciada en el sitio web. Una factura creada sin iniciar sesión no tiene propietario y no envía eventos; hoy eso incluye una factura creada con una clave API.

### Eventos de Transfer Package

Los cuatro eventos `package.*` se envían a la cuenta **propietaria del paquete**. Un paquete comprado por factura sin iniciar sesión ni usar una clave API no tiene propietario y no genera eventos. Tampoco los generan las facturas canceladas, las compras rechazadas ni las compras en revisión manual; un paquete en revisión envía `package.activated` cuando se activa.

Cada evento `package.*` incluye estos campos en `data`:

<ResponseField name="package_id" type="number">
  ID del paquete: el `id` en [Listar paquetes](/es/api-reference/transfer-packages/list).
</ResponseField>

<ResponseField name="address" type="string">
  La dirección que cubre el paquete.
</ResponseField>

<ResponseField name="status" type="string">
  Estado del paquete después del evento: `active` o `completed` en `package.transfer`, `completed` en `package.completed`, `active` en `package.activated`, `expired` en `package.expired`.
</ResponseField>

<ResponseField name="quota_total" type="number">
  Transferencias con las que se compró el paquete.
</ResponseField>

<ResponseField name="remaining" type="number">
  Transferencias que le quedan a este paquete después del cambio que informa el evento: un número absoluto, no una diferencia.
</ResponseField>

<Warning>
  **Los eventos pueden llegar desordenados.** Cada uno se entrega por separado, con reintentos durante unos 35 segundos, así que el `package.completed` causado por una transferencia puede llegar antes que el `package.transfer` de esa transferencia, y un `package.transfer` puede llegar antes que `package.activated`. Para cada `package_id`, conserve el `remaining` **más bajo** que haya visto: nunca aumenta. `completed` y `expired` son definitivos.
</Warning>

<Note>
  `remaining` también puede bajar sin evento. Un paquete de varias transferencias consume una transferencia al día como suscripción diaria —la primera al activarse, por eso un paquete de 500 transferencias empieza con `remaining: 499`— y ese cargo no se notifica. Dos transferencias desde la misma dirección en el mismo bloque pueden informar el mismo `remaining`. Tome `remaining` como una indicación y [Listar paquetes](/es/api-reference/transfer-packages/list) como la fuente de verdad.
</Note>

Para reconocer un reintento, use `(package_id, tx_hash)` en `package.transfer` y `(event, package_id)` en los demás: un reintento trae el mismo cuerpo, el mismo `timestamp` y la misma firma.

#### `package.transfer`

Una transferencia desde la dirección se pagó con un paquete. Se envía una vez **por cada paquete** al que se cargó la transferencia: casi siempre un evento por transferencia; una transferencia que tomó la última transferencia de un paquete y continuó en el siguiente genera un evento por cada uno.

<ResponseField name="tx_hash" type="string">
  La transacción de la transferencia en la cadena.
</ResponseField>

<ResponseField name="units" type="number">
  Transferencias tomadas de **este** paquete en esta transacción. Una transferencia a una dirección sin USDT necesita el doble de energía y cuenta como `2`, que pueden repartirse entre dos paquetes.
</ResponseField>

Aquí `status` es `completed` cuando esta transferencia agotó el paquete.

```json Response
{
  "event": "package.transfer",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 312,
    "tx_hash": "9f8e7d6c5b4a...",
    "units": 1
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.completed`

El paquete dejó de cubrir transferencias.

<ResponseField name="reason" type="string">
  `transfer`: una transferencia agotó el paquete; `subscription`: lo agotó el cargo diario; `manual`: soporte cerró el paquete. Tras `manual`, `remaining` puede ser mayor que cero, pero esas transferencias ya no se pueden usar.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  Con `reason: "transfer"`, la transferencia que cerró el paquete; `null` en los demás casos.
</ResponseField>

Un paquete sin saldo —por ejemplo, un paquete normal de una transferencia cuyo primer cargo diario tomó su única transferencia— se cierra con la siguiente transferencia sin un `package.transfer` propio: solo recibirá `package.completed` con el `tx_hash` de esa transferencia.

```json Response
{
  "event": "package.completed",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "quota_total": 500,
    "remaining": 0,
    "reason": "transfer",
    "tx_hash": "9f8e7d6c5b4a..."
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.activated`

El paquete se activó y desde ahora sus transferencias reciben energía. Se envía en cada activación, incluida una compra con saldo, cuya respuesta ya dice `active`, y el pago de una factura, que activa el paquete poco después de que el pago se ve en la cadena.

<ResponseField name="payment_method" type="string">
  Cómo se pagó el paquete: exactamente `balance`, `TRX` o `USDT`.
</ResponseField>

```json Response
{
  "event": "package.activated",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 499,
    "payment_method": "USDT"
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.expired`

La factura de un paquete no se pagó dentro de su plazo de 30 minutos. No se cobró nada; compre de nuevo para obtener una factura nueva. Sin campos adicionales; `remaining` es igual a `quota_total` y no se puede usar.

```json Response
{
  "event": "package.expired",
  "data": {
    "package_id": 319,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "expired",
    "quota_total": 500,
    "remaining": 500
  },
  "timestamp": "2026-10-15T15:21:16.986341+00:00"
}
```

### Entrega

- Hasta **3 intentos**, con pausas de **1 segundo** y luego **4 segundos** entre ellos. No hay pausa tras un éxito ni tras el último intento.
- Tiempo de espera de **10 segundos** por intento.
- Esperamos cualquier **`2xx`**. Cualquier otra cosa cuenta como intento fallido.
- **No se siguen las redirecciones.** Un `301`/`302` es un intento fallido, no un salto.
- Los eventos perdidos **no** se reenvían después. Si fallan los tres intentos, ese evento se pierde; concilie con [Consultar pedido](/es/api-reference/orders/get-order), [Obtener factura](/es/api-reference/invoices/get-invoice) o [Listar paquetes](/es/api-reference/transfer-packages/list) en lugar de esperar una repetición.
- **Los eventos no llegan en orden.** Cada uno se entrega por separado, así que uno posterior puede llegar antes. Un reintento lleva el mismo cuerpo, el mismo `timestamp` y la misma firma.
- Cada pedido de la cuenta envía eventos, también la recarga automática, así que una cuenta con mucha actividad recibe muchos. Responda `2xx` de inmediato y haga el trabajo pesado después de responder.

Su URL debe resolverse a una dirección **pública**. Se rechazan los rangos loopback, privados y link-local, y también un host que no resuelve: en ambos casos no se envía nada y no se escribe ninguna fila en el registro.

### Verificación de la firma

Cada petición lleva `X-Webhook-Signature: sha256=<hex>`, un HMAC-SHA256 sobre el **cuerpo bruto de la petición** con su secreto de webhook como clave.

Dos detalles deciden si su comprobación funciona:

1. **Quite el prefijo `sha256=`** antes de comparar. La cabecera no es un digest hexadecimal a secas.
2. **Aplique el hash a los bytes recibidos**, no a un objeto vuelto a serializar. Analizar el JSON y volcarlo de nuevo cambia el orden de las claves y los espacios, y la firma no coincidirá nunca.

Su secreto de firma aparece en [Dashboard → API](https://tronrental.com/dashboard/api) junto a la URL del webhook. No se devuelve a las peticiones con clave API: para leerlo hay que iniciar sesión en el sitio web.

<CodeGroup>
```python Python
import hashlib
import hmac

def verify_webhook(raw_body: bytes, signature_header: str, secret: str) -> bool:
    prefix, _, received = signature_header.partition("=")
    if prefix != "sha256" or not received:
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received)
```

```javascript JavaScript
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const [prefix, received] = String(signatureHeader).split("=");
  if (prefix !== "sha256" || !received) return false;
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```
</CodeGroup>

<Warning>
  Verifique la firma antes de actuar sobre el contenido y compare en tiempo constante (`hmac.compare_digest` / `crypto.timingSafeEqual`). Comparar con `==` filtra información por tiempo.
</Warning>
