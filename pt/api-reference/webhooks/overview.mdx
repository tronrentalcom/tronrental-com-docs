## Webhooks

Sua conta tem **uma única URL de webhook**, e todos os eventos vão para ela. Defina-a em [Dashboard → API](https://tronrental.com/dashboard/api) ou por meio de [Configurar webhook](/pt/api-reference/webhooks/configure).

### Eventos

Hoje existem dez eventos.

| Evento | Quando é enviado |
|-------|-----------|
| `order.updated` | Um pedido de energia ou largura de banda da sua conta muda de estado, seja qual for a origem: API, site, bot do Telegram ou recarga automática |
| `activation.updated` | Uma ativação de endereço paga com o seu saldo foi concluída |
| `withdrawal.completed` | Um saque do seu saldo foi enviado |
| `withdrawal.failed` | Um saque foi recusado e o valor voltou ao seu saldo |
| `invoice.updated` | Uma fatura da sua conta muda de status |
| `subscription.transfer` | O Smart Mode pagou por uma transferência de um endereço monitorado |
| `package.transfer` | Um Transfer Package pagou por uma transferência do seu endereço |
| `package.completed` | Um Transfer Package deixou de cobrir transferências |
| `package.activated` | Um Transfer Package foi ativado |
| `package.expired` | A fatura não paga de um Transfer Package expirou |

<Note>
  Desde 3 de novembro de 2026, `order.updated` cobre **todos os pedidos da conta**; antes, era enviado só para pedidos criados com uma chave de API. Distinga os canais pelo campo `source`. Os [aluguéis de largura de banda](/pt/api-reference/bandwidth-rentals/create-rental) não enviam eventos.
</Note>

### Envelope

Toda entrega tem as mesmas três chaves de nível superior. `timestamp` é o momento em que montamos o evento, ISO-8601 em UTC.

```json Response
{
  "event": "order.updated",
  "data": { },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

Cabeçalhos:

| Cabeçalho | Valor |
|--------|-------|
| `Content-Type` | `application/json` |
| `X-Webhook-Signature` | `sha256=<hex>` — veja a seção «Verificação da assinatura» abaixo |
| `Host` | o host da sua URL |

### `order.updated`

<ResponseField name="id" type="number">
  ID do pedido.
</ResponseField>

<ResponseField name="type" type="string">
  `energy` ou `bandwidth`.
</ResponseField>

<ResponseField name="status" type="string">
  `processing`, `filled`, `partial`, `failed`, `reclaimed` ou `reclaim_failed`. **Este campo é a fonte da verdade** — veja o aviso abaixo.
</ResponseField>

<ResponseField name="source" type="string">
  Onde o pedido foi feito: `api`, `web` (o site), `bot` (o bot do Telegram), `autorefill` (uma regra de [Recarga automática](/pt/api-reference/auto-refill/overview)), `faucet` (largura de banda gratuita) ou `broadcast` (Energy Broadcast).
</ResponseField>

<ResponseField name="target_address" type="string">
  Endereço para o qual o recurso foi delegado.
</ResponseField>

<ResponseField name="volume" type="number">
  Quantidade pedida — unidades de energia ou pontos de bandwidth.
</ResponseField>

<ResponseField name="expected_volume" type="number">
  O mesmo que `volume`. Existe para que o esperado e o entregue possam ser comparados sem descobrir qual campo significa o quê.
</ResponseField>

<ResponseField name="delivered_volume" type="number">
  Quanto foi de fato delegado até agora. Igual a `volume` quando o pedido está `filled`; em `processing` e `partial` é a soma das partes já entregues, e `0` em caso de falha.
</ResponseField>

<ResponseField name="price_trx" type="string">
  Preço do pedido em TRX, como string decimal.
</ResponseField>

<ResponseField name="delegate_txid" type="string | null">
  Transação que delegou o recurso.
</ResponseField>

<ResponseField name="undelegate_txid" type="string | null">
  Transação que o retomou ao fim da locação.
</ResponseField>

<ResponseField name="reclaim_at" type="string | null">
  Quando o recurso está agendado para ser retomado, ISO-8601, ou `null` para pedidos que não são retomados por temporizador.
</ResponseField>

```json Response
{
  "event": "order.updated",
  "data": {
    "id": 247033,
    "type": "energy",
    "status": "filled",
    "source": "web",
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "volume": 65000,
    "expected_volume": 65000,
    "delivered_volume": 65000,
    "price_trx": "2.75",
    "delegate_txid": "a1b2c3d4e5f6...",
    "undelegate_txid": null,
    "reclaim_at": "2026-09-15T07:44:56+00:00"
  },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

<Warning>
**Julgue o resultado pelo `status`, nunca pela presença de `delegate_txid`.** Um pedido que falhou também pode trazer um id de transação — nós o mantemos de propósito, para que a falha possa ser investigada. Só o `status` diz se você recebeu o recurso.
</Warning>

Internamente dividimos pedidos grandes em partes, mas isso é problema nosso: você recebe **um webhook por pedido**, nunca um por parte.

O mesmo `status` pode chegar mais de uma vez para um pedido. Use `(id, status)` como chave e ignore a repetição.

### `activation.updated`

Enviado quando uma ativação paga com o seu saldo é concluída: feita com [Ativar Endereço](/pt/api-reference/energy/activate-address), no site ou automaticamente, quando um pedido ou um Transfer Package precisa ativar um endereço inativo.

<ResponseField name="id" type="number">
  ID do registro de ativação — o `id` que Ativar Endereço retorna.
</ResponseField>

<ResponseField name="target_address" type="string">
  O endereço que foi ativado.
</ResponseField>

<ResponseField name="status" type="string">
  `completed` — enviamos a ativação à rede; `already_activated` — o endereço já estava ativo e nada foi cobrado; `failed` — a ativação não aconteceu e a cobrança foi estornada; `pending` — a transação foi enviada, mas o resultado ainda não é conhecido, então a cobrança fica retida até verificarmos.
</ResponseField>

<ResponseField name="txid" type="string | null">
  A transação de ativação, ou `null` quando não há.
</ResponseField>

<ResponseField name="cost_trx" type="string">
  Quanto a ativação custou para você no fim, como string decimal: `0` após um estorno e para um endereço que já estava ativo.
</ResponseField>

```json Response
{
  "event": "activation.updated",
  "data": {
    "id": 12345,
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "txid": "a1b2c3d4e5f6...",
    "cost_trx": "1.2"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Note>
  `pending` é raro, e hoje o resultado final não envia um segundo evento. Se uma ativação continuar em `pending`, fale com o suporte.
</Note>

### `withdrawal.completed` e `withdrawal.failed`

Enviados quando um saque do seu saldo tem resultado, seja qual for a forma do pedido: [Criar Saque](/pt/api-reference/account/withdrawals), o site ou o bot do Telegram. `withdrawal.completed` — a transação foi enviada à rede TRON; `withdrawal.failed` — o saque foi recusado e `total_trx` voltou ao seu saldo.

<ResponseField name="id" type="number">
  ID do saque — o `id` que Criar Saque retorna.
</ResponseField>

<ResponseField name="status" type="string">
  `completed` ou `failed` — o mesmo valor do nome do evento.
</ResponseField>

<ResponseField name="currency" type="string">
  `TRX` ou `USDT`.
</ResponseField>

<ResponseField name="to_address" type="string">
  O endereço de destino.
</ResponseField>

<ResponseField name="amount_trx" type="string">
  O valor enviado em TRX, como string decimal. Num saque de USDT, o equivalente em TRX que foi cobrado.
</ResponseField>

<ResponseField name="fee_trx" type="string">
  A taxa em TRX.
</ResponseField>

<ResponseField name="total_trx" type="string">
  O que foi cobrado do seu saldo: `amount_trx` + `fee_trx`.
</ResponseField>

<ResponseField name="amount_usdt" type="string | null">
  O valor em USDT enviado num saque de USDT; caso contrário, `null`.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  A transação em `withdrawal.completed`; `null` em `withdrawal.failed`.
</ResponseField>

<ResponseField name="refunded_trx" type="string | null">
  O que voltou ao seu saldo em `withdrawal.failed` (`total_trx`); `null` em `withdrawal.completed`.
</ResponseField>

<ResponseField name="created_at" type="string">
  Quando o saque foi pedido, ISO-8601 UTC.
</ResponseField>

### `invoice.updated`

Enviado à conta dona da fatura quando o status dela muda. `data` é o objeto que [Consultar Fatura](/pt/api-reference/invoices/get-invoice) retorna, com duas diferenças: `error_message` é sempre `null`, e `status` é o status que este evento anuncia.

| `status` | Significado |
|----------|---------|
| `paid` | Pagamento recebido, entrega em andamento |
| `underpaid` | Chegou menos que o preço; `topup_until` diz até quando o restante pode ser enviado |
| `delegated` | O recurso foi delegado |
| `failed` | A entrega falhou |
| `expired` | Nenhum pagamento chegou antes de a fatura expirar |
| `reclaimed` | O aluguel terminou e o recurso foi retirado |
| `reclaim_failed` | Não foi possível retirar o recurso |

    "energy_amount": 65000,

    "price_trx": "2.75",

    "error_message": null,

<Warning>

Uma fatura pertence à sua conta quando você a criou com a sessão iniciada no site. Uma fatura criada sem login não tem dono e não envia eventos — e hoje isso inclui uma fatura criada com uma chave de API.

### Eventos de Transfer Package

Os quatro eventos `package.*` vão para a conta **dona do pacote**. Um pacote comprado por fatura sem login nem chave de API não tem dono e não gera eventos. Faturas canceladas, compras recusadas e compras em revisão manual também não geram eventos; um pacote em revisão envia `package.activated` quando for ativado.

Todo evento `package.*` traz estes campos em `data`:

<ResponseField name="package_id" type="number">
  ID do pacote — o `id` em [Listar Pacotes](/pt/api-reference/transfer-packages/list).
</ResponseField>

<ResponseField name="address" type="string">
  O endereço que o pacote atende.
</ResponseField>

<ResponseField name="status" type="string">
  Status do pacote após o evento: `active` ou `completed` em `package.transfer`, `completed` em `package.completed`, `active` em `package.activated`, `expired` em `package.expired`.
</ResponseField>

<ResponseField name="quota_total" type="number">
  Transferências com que o pacote foi comprado.
</ResponseField>

<ResponseField name="remaining" type="number">
  Transferências que restam neste pacote após a mudança informada pelo evento — um número absoluto, não uma diferença.
</ResponseField>

<Warning>
  **Os eventos podem chegar fora de ordem.** Cada um é entregue separadamente, com novas tentativas por cerca de 35 segundos, então o `package.completed` causado por uma transferência pode chegar antes do `package.transfer` dessa transferência, e um `package.transfer` pode chegar antes de `package.activated`. Para cada `package_id`, guarde o **menor** `remaining` que já viu: ele nunca aumenta. `completed` e `expired` são definitivos.
</Warning>

<Note>
  `remaining` também pode diminuir sem evento. Um pacote de várias transferências consome uma transferência por dia como assinatura diária — a primeira na ativação, por isso um pacote de 500 transferências começa com `remaining: 499` — e essa cobrança não é anunciada. Duas transferências do mesmo endereço no mesmo bloco podem informar o mesmo `remaining`. Trate `remaining` como uma indicação e [Listar Pacotes](/pt/api-reference/transfer-packages/list) como a fonte da verdade.
</Note>

Para reconhecer uma nova tentativa, use `(package_id, tx_hash)` em `package.transfer` e `(event, package_id)` nos demais: a nova tentativa traz o mesmo corpo, o mesmo `timestamp` e a mesma assinatura.

#### `package.transfer`

Uma transferência do endereço foi paga com um pacote. Enviado uma vez **por pacote** cobrado pela transferência — quase sempre um evento por transferência; uma transferência que usou a última transferência de um pacote e continuou no seguinte gera um evento para cada um.

<ResponseField name="tx_hash" type="string">
  A transação da transferência na blockchain.
</ResponseField>

<ResponseField name="units" type="number">
  Transferências descontadas **deste** pacote nesta transação. Uma transferência para um endereço sem USDT precisa do dobro de energia e conta como `2`, que podem ser divididas entre dois pacotes.
</ResponseField>

Aqui `status` é `completed` quando esta transferência esgotou o pacote.

```json Response
{
  "event": "package.transfer",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 312,
    "tx_hash": "9f8e7d6c5b4a...",
    "units": 1
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.completed`

O pacote deixou de cobrir transferências.

<ResponseField name="reason" type="string">
  `transfer` — uma transferência esgotou o pacote; `subscription` — a cobrança diária o esgotou; `manual` — o suporte encerrou o pacote. Depois de `manual`, `remaining` pode ser maior que zero, mas essas transferências não podem mais ser usadas.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  Com `reason: "transfer"`, a transferência que encerrou o pacote; `null` nos demais casos.
</ResponseField>

Um pacote sem saldo — por exemplo, um pacote comum de uma transferência cuja primeira cobrança diária levou sua única transferência — é encerrado pela transferência seguinte sem um `package.transfer` próprio: você recebe apenas `package.completed` com o `tx_hash` dessa transferência.

```json Response
{
  "event": "package.completed",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "quota_total": 500,
    "remaining": 0,
    "reason": "transfer",
    "tx_hash": "9f8e7d6c5b4a..."
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.activated`

O pacote foi ativado e a partir de agora suas transferências recebem energia. Enviado a cada ativação — inclusive em uma compra com saldo, cuja resposta já diz `active`, e no pagamento de uma fatura, que ativa o pacote pouco depois de o pagamento aparecer na blockchain.

<ResponseField name="payment_method" type="string">
  Como o pacote foi pago: exatamente `balance`, `TRX` ou `USDT`.
</ResponseField>

```json Response
{
  "event": "package.activated",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 499,
    "payment_method": "USDT"
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.expired`

A fatura de um pacote não foi paga dentro do prazo de 30 minutos. Nada foi cobrado; compre novamente para obter uma nova fatura. Sem campos extras; `remaining` é igual a `quota_total` e não pode ser usado.

```json Response
{
  "event": "package.expired",
  "data": {
    "package_id": 319,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "expired",
    "quota_total": 500,
    "remaining": 500
  },
  "timestamp": "2026-10-15T15:21:16.986341+00:00"
}
```

### Entrega

- Até **3 tentativas**, com pausas de **1 segundo** e depois **4 segundos** entre elas. Não há pausa após um sucesso nem após a última tentativa.
- Tempo limite de **10 segundos** por tentativa.
- Esperamos qualquer **`2xx`**. Qualquer outra coisa conta como tentativa falha.
- **Redirecionamentos não são seguidos.** Um `301`/`302` é uma tentativa falha, não um salto.
- Eventos perdidos **não** são reenviados depois. Se as três tentativas falharem, aquele evento se perdeu; reconcilie com [Consultar pedido](/pt/api-reference/orders/get-order), [Consultar Fatura](/pt/api-reference/invoices/get-invoice) ou [Listar Pacotes](/pt/api-reference/transfer-packages/list) em vez de esperar uma repetição.
- **Os eventos não têm ordem garantida.** Cada um é entregue separadamente, então um evento posterior pode chegar primeiro. Uma nova tentativa traz o mesmo corpo, o mesmo `timestamp` e a mesma assinatura.
- Todo pedido da conta envia eventos, inclusive a recarga automática, então uma conta movimentada recebe muitos. Responda `2xx` na hora e faça o trabalho pesado depois da resposta.

Sua URL precisa resolver para um endereço **público**. Faixas de loopback, privadas e link-local são recusadas, assim como um host que não resolve — em ambos os casos nada é enviado e nenhuma linha de registro é escrita.

### Verificação da assinatura

Toda requisição traz `X-Webhook-Signature: sha256=<hex>`, um HMAC-SHA256 sobre o **corpo bruto da requisição**, com o seu segredo de webhook como chave.

Dois detalhes decidem se a sua verificação funciona:

1. **Remova o prefixo `sha256=`** antes de comparar. O cabeçalho não é um digest hexadecimal puro.
2. **Faça o hash dos bytes recebidos**, não de um objeto reserializado. Analisar o JSON e serializá-lo de novo muda a ordem das chaves e os espaços, e a assinatura nunca vai bater.

Seu segredo de assinatura aparece em [Dashboard → API](https://tronrental.com/dashboard/api), ao lado da URL do webhook. Ele não é devolvido a requisições com chave de API — para lê-lo é preciso entrar no site.

<CodeGroup>
```python Python
import hashlib
import hmac

def verify_webhook(raw_body: bytes, signature_header: str, secret: str) -> bool:
    prefix, _, received = signature_header.partition("=")
    if prefix != "sha256" or not received:
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received)
```

```javascript JavaScript
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const [prefix, received] = String(signatureHeader).split("=");
  if (prefix !== "sha256" || !received) return false;
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```
</CodeGroup>

<Warning>
  Verifique a assinatura antes de agir sobre o conteúdo e compare em tempo constante (`hmac.compare_digest` / `crypto.timingSafeEqual`). Comparar com `==` vaza por tempo.
</Warning>
