## Вебхуки

У аккаунта **один URL вебхука**, и все события уходят на него. Задайте его в [Dashboard → API](https://tronrental.com/dashboard/api) или через [Настройку вебхука](/ru/api-reference/webhooks/configure).

### События

Сегодня существует шесть событий.

| Событие | Когда отправляется |
|-------|-----------|
| `order.updated` | Заказ энергии или bandwidth сменил состояние — **только для заказов, созданных через API** |
| `subscription.transfer` | Smart Mode оплатил перевод с отслеживаемого адреса |
| `package.transfer` | Transfer Package оплатил перевод со своего адреса |
| `package.completed` | Transfer Package перестал обслуживать переводы |
| `package.activated` | Transfer Package стал активным |
| `package.expired` | Истёк неоплаченный инвойс Transfer Package |

<Warning>
  `order.updated` отправляется только для заказов, созданных с API-ключом. Покупки на сайте и через Telegram-бота вебхук не порождают — при том что события Smart Mode тот же аккаунт получает как обычно.
</Warning>

### Конверт

У каждой доставки три одинаковых ключа верхнего уровня. `timestamp` — момент, когда мы собрали событие, ISO-8601 в UTC.

```json Response
{
  "event": "order.updated",
  "data": { },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

Заголовки:

| Заголовок | Значение |
|--------|-------|
| `Content-Type` | `application/json` |
| `X-Webhook-Signature` | `sha256=<hex>` — см. раздел «Проверка подписи» ниже |
| `Host` | хост вашего URL |

### `order.updated`

<ResponseField name="id" type="number">
  ID заказа.
</ResponseField>

<ResponseField name="type" type="string">
  `energy` или `bandwidth`.
</ResponseField>

<ResponseField name="status" type="string">
  `processing`, `filled`, `partial`, `failed`, `reclaimed` или `reclaim_failed`. **Это поле — источник истины**, см. предупреждение ниже.
</ResponseField>

<ResponseField name="target_address" type="string">
  Адрес, которому делегирован ресурс.
</ResponseField>

<ResponseField name="volume" type="number">
  Заказанный объём — единицы энергии или пункты bandwidth.
</ResponseField>

<ResponseField name="expected_volume" type="number">
  То же, что `volume`. Присутствует, чтобы сравнивать ожидаемое с доставленным, не выясняя, какое поле что означает.
</ResponseField>

<ResponseField name="delivered_volume" type="number">
  Сколько фактически делегировано на данный момент. Равно `volume`, когда заказ `filled`; на `processing` и `partial` — сумма уже выданных частей; `0` при отказе.
</ResponseField>

<ResponseField name="price_trx" type="string">
  Цена заказа в TRX, десятичной строкой.
</ResponseField>

<ResponseField name="delegate_txid" type="string | null">
  Транзакция, которой ресурс делегирован.
</ResponseField>

<ResponseField name="undelegate_txid" type="string | null">
  Транзакция, которой его забрали обратно по окончании аренды.
</ResponseField>

<ResponseField name="reclaim_at" type="string | null">
  Когда ресурс запланировано отозвать, ISO-8601, либо `null` для заказов без таймера отзыва.
</ResponseField>

```json Response
{
  "event": "order.updated",
  "data": {
    "id": 247033,
    "type": "energy",
    "status": "filled",
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "volume": 65000,
    "expected_volume": 65000,
    "delivered_volume": 65000,
    "price_trx": "2.75",
    "delegate_txid": "a1b2c3d4e5f6...",
    "undelegate_txid": null,
    "reclaim_at": "2026-09-15T07:44:56+00:00"
  },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

<Warning>
**Судите об исходе по `status`, а не по наличию `delegate_txid`.** У неуспешного заказа идентификатор транзакции тоже может быть заполнен — мы оставляем его намеренно, чтобы отказ можно было расследовать. Получен ли ресурс, говорит только `status`.
</Warning>

Крупный заказ мы внутри делим на части, но это наша кухня: вы получаете **один вебхук на заказ**, а не по одному на часть.

### События Transfer Package

Четыре события `package.*` уходят аккаунту, которому **принадлежит пакет**. У пакета, купленного по инвойсу без входа в аккаунт и без API-ключа, владельца нет, и событий по нему не будет. Не будет их и по отменённым инвойсам, отклонённым покупкам и покупкам на ручной проверке; пакет с проверки пришлёт `package.activated`, когда будет активирован.

Каждое событие `package.*` несёт в `data` эти поля:

<ResponseField name="package_id" type="number">
  ID пакета — `id` в [Списке пакетов](/ru/api-reference/transfer-packages/list).
</ResponseField>

<ResponseField name="address" type="string">
  Адрес, который обслуживает пакет.
</ResponseField>

<ResponseField name="status" type="string">
  Статус пакета после события: `active` или `completed` у `package.transfer`, `completed` у `package.completed`, `active` у `package.activated`, `expired` у `package.expired`.
</ResponseField>

<ResponseField name="quota_total" type="number">
  Сколько переводов было в пакете при покупке.
</ResponseField>

<ResponseField name="remaining" type="number">
  Сколько переводов осталось в пакете после изменения, о котором сообщает событие, — абсолютное число, а не разница.
</ResponseField>

<Warning>
  **События могут прийти не по порядку.** Каждое доставляется отдельно, с повторами примерно до 35 секунд, поэтому `package.completed`, вызванное переводом, может прийти раньше `package.transfer` этого перевода, а `package.transfer` — раньше `package.activated`. Для каждого `package_id` храните **наименьший** увиденный `remaining`: он никогда не растёт. Статусы `completed` и `expired` окончательные.
</Warning>

<Note>
  `remaining` может уменьшиться и без события. Пакет на несколько переводов списывает один перевод в сутки как суточную подписку — первый при активации, поэтому пакет на 500 переводов начинается с `remaining: 499`, — и об этом списании событие не приходит. Два перевода с одного адреса в одном блоке могут прислать одинаковый `remaining`. Считайте `remaining` подсказкой, а источником правды — [Список пакетов](/ru/api-reference/transfer-packages/list).
</Note>

Чтобы распознать повтор, используйте `(package_id, tx_hash)` для `package.transfer` и `(event, package_id)` для остальных: повтор приходит с тем же телом, тем же `timestamp` и той же подписью.

#### `package.transfer`

Перевод с адреса оплачен из пакета. Отправляется по одному разу **на каждый пакет**, с которого списан перевод, — почти всегда одно событие на перевод; перевод, забравший последний перевод одного пакета и продолжившийся на следующем, даёт по событию на каждый.

<ResponseField name="tx_hash" type="string">
  Транзакция перевода в сети.
</ResponseField>

<ResponseField name="units" type="number">
  Сколько переводов списано с **этого** пакета за эту транзакцию. Перевод на адрес, где нет USDT, требует двойной энергии и считается за `2` — их можно разделить между двумя пакетами.
</ResponseField>

Здесь `status` равен `completed`, если этот перевод исчерпал пакет.

```json Response
{
  "event": "package.transfer",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 312,
    "tx_hash": "9f8e7d6c5b4a...",
    "units": 1
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.completed`

Пакет перестал обслуживать переводы.

<ResponseField name="reason" type="string">
  `transfer` — пакет исчерпан переводом; `subscription` — его исчерпало суточное списание; `manual` — пакет закрыла поддержка. После `manual` значение `remaining` может быть больше нуля, но эти переводы использовать уже нельзя.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  При `reason: "transfer"` — перевод, закрывший пакет; иначе `null`.
</ResponseField>

Пакет без остатка — например, обычный пакет на один перевод, у которого первое суточное списание забрало единственный перевод, — закрывается следующим переводом без собственного `package.transfer`: придёт только `package.completed` с `tx_hash` этого перевода.

```json Response
{
  "event": "package.completed",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "quota_total": 500,
    "remaining": 0,
    "reason": "transfer",
    "tx_hash": "9f8e7d6c5b4a..."
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.activated`

Пакет стал активным, и с этого момента его переводы получают энергию. Отправляется при каждой активации — в том числе при покупке с баланса, хотя её ответ уже содержит `active`, и при оплате инвойса, которая активирует пакет вскоре после того, как платёж виден в сети.

<ResponseField name="payment_method" type="string">
  Как оплачен пакет: ровно `balance`, `TRX` или `USDT`.
</ResponseField>

```json Response
{
  "event": "package.activated",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 499,
    "payment_method": "USDT"
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.expired`

Инвойс на пакет не оплачен за отведённые 30 минут. Ничего не списано; чтобы получить новый инвойс, купите заново. Дополнительных полей нет; `remaining` равен `quota_total` и для использования недоступен.

```json Response
{
  "event": "package.expired",
  "data": {
    "package_id": 319,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "expired",
    "quota_total": 500,
    "remaining": 500
  },
  "timestamp": "2026-10-15T15:21:16.986341+00:00"
}
```

### Доставка

- До **3 попыток**, с паузами **1 секунда** и затем **4 секунды** между ними. После успеха и после последней попытки пауз нет.
- Таймаут **10 секунд** на попытку.
- Мы ждём любой **`2xx`**. Всё остальное считается неудачной попыткой.
- **Редиректы не следуются.** `301`/`302` — это неудачная попытка, а не переход.
- Пропущенные события **не досылаются**. Если все три попытки не удались, событие потеряно; сверяйтесь через [Получение заказа](/ru/api-reference/orders/get-order) или [Список пакетов](/ru/api-reference/transfer-packages/list), а не ждите повтора.

Ваш URL обязан резолвиться в **публичный** адрес. Loopback, приватные и link-local диапазоны отвергаются, как и хост, который вообще не резолвится — в обоих случаях ничего не отправляется и строка в журнале не пишется.

### Проверка подписи

Каждый запрос несёт `X-Webhook-Signature: sha256=<hex>` — HMAC-SHA256 по **сырому телу запроса** с вашим секретом вебхука.

Работоспособность вашей проверки решают две детали:

1. **Отрежьте префикс `sha256=`** перед сравнением. В заголовке не голый hex-дайджест.
2. **Хешируйте полученные байты**, а не пересобранный объект. Разбор JSON и повторная сериализация меняют порядок ключей и пробелы — подпись не сойдётся никогда.

Секрет подписи показан в [Dashboard → API](https://tronrental.com/dashboard/api) рядом с URL вебхука. По API-ключу он не отдаётся — чтобы его прочитать, нужно войти на сайте.

<CodeGroup>
```python Python
import hashlib
import hmac

def verify_webhook(raw_body: bytes, signature_header: str, secret: str) -> bool:
    prefix, _, received = signature_header.partition("=")
    if prefix != "sha256" or not received:
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received)
```

```javascript JavaScript
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const [prefix, received] = String(signatureHeader).split("=");
  if (prefix !== "sha256" || !received) return false;
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}
```
</CodeGroup>

<Warning>
  Проверяйте подпись до того, как действовать по содержимому, и сравнивайте за постоянное время (`hmac.compare_digest` / `crypto.timingSafeEqual`). Сравнение через `==` утекает по таймингу.
</Warning>
