## Webhooks

Your account has **one webhook URL**, and every event goes to it. Set it in [Dashboard → API](https://tronrental.com/dashboard/api), or with [Configure Webhook](/api-reference/webhooks/configure).

### Events

Eight events exist today.

| Event | Sent when |
|-------|-----------|
| `order.updated` | An energy or bandwidth order of your account changes state — however it was placed: API, website, Telegram bot or auto-refill |
| `activation.updated` | An address activation paid from your balance is settled |
| `invoice.updated` | An invoice that belongs to your account changes status |
| `subscription.transfer` | Smart Mode paid for a transfer on a watched address |
| `package.transfer` | A Transfer Package paid for a transfer from its address |
| `package.completed` | A Transfer Package stopped serving transfers |
| `package.activated` | A Transfer Package became active |
| `package.expired` | An unpaid Transfer Package invoice expired |

<Note>
  Since November 3, 2026, `order.updated` covers **every order of the account**; before that it was sent only for orders created with an API key. Tell the channels apart by its `source` field. [Bandwidth rentals](/api-reference/bandwidth-rentals/create-rental) send no events.
</Note>

### Envelope

Every delivery has the same three top-level keys. `timestamp` is the moment we built the event, ISO-8601 in UTC.

```json Response
{
  "event": "order.updated",
  "data": { },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

Headers:

| Header | Value |
|--------|-------|
| `Content-Type` | `application/json` |
| `X-Webhook-Signature` | `sha256=<hex>` — see [Verifying the signature](#verifying-the-signature) |
| `Host` | the host of your URL |

### `order.updated`

<ResponseField name="id" type="number">
  Order ID.
</ResponseField>

<ResponseField name="type" type="string">
  `energy` or `bandwidth`.
</ResponseField>

<ResponseField name="status" type="string">
  `processing`, `filled`, `partial`, `failed`, `reclaimed` or `reclaim_failed`. **This field is the source of truth** — see the warning below.
</ResponseField>

<ResponseField name="source" type="string">
  Where the order was placed: `api`, `web` (the website), `bot` (the Telegram bot), `autorefill` (an [Auto Refill](/api-reference/auto-refill/overview) rule), `faucet` (free bandwidth) or `broadcast` (Energy Broadcast).
</ResponseField>

<ResponseField name="target_address" type="string">
  The address the resource was delegated to.
</ResponseField>

<ResponseField name="volume" type="number">
  The ordered amount — energy units, or bandwidth points.
</ResponseField>

<ResponseField name="expected_volume" type="number">
  Same as `volume`. Present so that expected and delivered can be compared without knowing which field means what.
</ResponseField>

<ResponseField name="delivered_volume" type="number">
  How much has actually been delegated so far. Equals `volume` once the order is `filled`; on `processing` and `partial` it is the sum of the chunks delegated up to now, and `0` on failure.
</ResponseField>

<ResponseField name="price_trx" type="string">
  Order price in TRX, as a decimal string.
</ResponseField>

<ResponseField name="delegate_txid" type="string | null">
  Transaction that delegated the resource.
</ResponseField>

<ResponseField name="undelegate_txid" type="string | null">
  Transaction that took it back, once the rental ends.
</ResponseField>

<ResponseField name="reclaim_at" type="string | null">
  When the resource is scheduled to be reclaimed, ISO-8601, or `null` for orders that are not reclaimed on a timer.
</ResponseField>

<ResponseField name="fail_reason" type="string | null">
  Why a `failed` order failed, as a code from the **Failure reasons** table on [Get Order](/api-reference/orders/get-order); `null` for any other status. Treat a code you do not know as `internal_error`: new codes may be added.
</ResponseField>

<ResponseField name="refunded_trx" type="string | null">
  What went back to your balance, in TRX, as a decimal string: the full `price_trx` for `failed`, the price of the undelivered part for `partial`; `null` when nothing was refunded.
</ResponseField>

```json Response
{
  "event": "order.updated",
  "data": {
    "id": 247033,
    "type": "energy",
    "status": "filled",
    "source": "web",
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "volume": 65000,
    "expected_volume": 65000,
    "delivered_volume": 65000,
    "price_trx": "2.75",
    "delegate_txid": "a1b2c3d4e5f6...",
    "undelegate_txid": null,
    "reclaim_at": "2026-09-15T07:44:56+00:00",
    "fail_reason": null,
    "refunded_trx": null
  },
  "timestamp": "2026-09-14T14:51:16.986341+00:00"
}
```

<Warning>
**Judge the outcome by `status`, never by the presence of `delegate_txid`.** A failed order can carry a transaction id — we keep it deliberately so that a failure can be investigated. Only `status` says whether you got the resource.
</Warning>

A large order is split into chunks internally, but that is our business: you receive **one webhook per order**, never one per chunk.

The same `status` can arrive more than once for one order. Treat `(id, status)` as the key and ignore a repeat.

### `activation.updated`

Sent when an activation paid from your balance is settled: one made with [Activate Address](/api-reference/energy/activate-address), on the website, or automatically when an order or a Transfer Package needs an inactive address activated.

<ResponseField name="id" type="number">
  Activation record ID — the `id` that Activate Address returns.
</ResponseField>

<ResponseField name="target_address" type="string">
  The address that was activated.
</ResponseField>

<ResponseField name="status" type="string">
  `completed` — we broadcast the activation; `already_activated` — the address was already active and nothing was charged; `failed` — the activation did not happen and the charge was refunded; `pending` — the transaction was sent but its outcome is not known yet, so the charge is held until we check it.
</ResponseField>

<ResponseField name="txid" type="string | null">
  The activation transaction, or `null` when there is none.
</ResponseField>

<ResponseField name="cost_trx" type="string">
  What the activation cost you in the end, as a decimal string: `0` after a refund and for an address that was already active.
</ResponseField>

```json Response
{
  "event": "activation.updated",
  "data": {
    "id": 12345,
    "target_address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "txid": "a1b2c3d4e5f6...",
    "cost_trx": "1.2"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Note>
  `pending` is rare, and its final outcome does not send a second event today. If an activation stays `pending`, contact support.
</Note>

### `invoice.updated`

Sent to the account that owns the invoice when its status changes. `data` is the object [Get Invoice](/api-reference/invoices/get-invoice) returns, with two differences: `error_message` is always `null`, and `status` is the status this event announces.

| `status` | Meaning |
|----------|---------|
| `paid` | Payment received, delivery in progress |
| `underpaid` | Less than the price arrived; `topup_until` says until when the rest can be sent |
| `delegated` | The resource was delegated |
| `failed` | Delivery failed |
| `expired` | No payment arrived before the invoice expired |
| `reclaimed` | The rental ended and the resource was taken back |
| `reclaim_failed` | Taking the resource back failed |

```json Response
{
  "event": "invoice.updated",
  "data": {
    "invoice_id": "7c1f0c2a-3b4d-4e5f-8a9b-0c1d2e3f4a5b",
    "payment_address": "TPaymentAddress...",
    "target_address": "TRecipientAddress...",
    "energy_amount": 65000,
    "duration": "1h",
    "price_trx": "2.75",
    "price_usdt": "0.64",
    "status": "delegated",
    "error_message": null,
    "tx_hash": "a1b2c3d4e5f6...",
    "paid_at": "2026-11-03T14:50:40+00:00",
    "completed_at": "2026-11-03T14:51:16+00:00",
    "expires_at": "2026-11-03T15:20:00+00:00",
    "created_at": "2026-11-03T14:50:00+00:00"
  },
  "timestamp": "2026-11-03T14:51:16.986341+00:00"
}
```

<Warning>
  **A status can repeat, and events can arrive out of order** — a `delegated` can come before the `paid` that preceded it. When the exact state matters, confirm it with [Get Invoice](/api-reference/invoices/get-invoice).
</Warning>

An invoice belongs to your account when you created it while signed in on the website. An invoice created without signing in has no owner and sends no events — and today that includes an invoice created with an API key.

### Transfer Package events

The four `package.*` events go to the account that **owns the package**. A package bought by invoice without signing in or an API key has no owner and produces no events. Cancelled invoices, refused purchases and purchases held for manual review produce no events either; a held package sends `package.activated` once it is activated.

Every `package.*` event carries these fields in `data`:

<ResponseField name="package_id" type="number">
  Package ID — the `id` in [List Packages](/api-reference/transfer-packages/list).
</ResponseField>

<ResponseField name="address" type="string">
  The address the package serves.
</ResponseField>

<ResponseField name="status" type="string">
  Package status after the event: `active` or `completed` for `package.transfer`, `completed` for `package.completed`, `active` for `package.activated`, `expired` for `package.expired`.
</ResponseField>

<ResponseField name="quota_total" type="number">
  Transfers the package was bought with.
</ResponseField>

<ResponseField name="remaining" type="number">
  Transfers left on this package after the change the event reports — an absolute number, not a difference.
</ResponseField>

<Warning>
  **Events can arrive out of order.** Each one is delivered on its own, with retries for up to about 35 seconds, so the `package.completed` caused by a transfer can arrive before that transfer's `package.transfer`, and a `package.transfer` can arrive before `package.activated`. For each `package_id`, keep the **lowest** `remaining` you have seen: it never grows. `completed` and `expired` are final.
</Warning>

<Note>
  `remaining` can also go down without an event. A multi-transfer package takes one transfer a day as its daily subscription — the first one at activation, which is why a 500-transfer package starts at `remaining: 499` — and that charge is not announced. Two transfers from the same address in the same block can report the same `remaining`. Treat `remaining` as a hint and [List Packages](/api-reference/transfer-packages/list) as the source of truth.
</Note>

To recognise a retry, use `(package_id, tx_hash)` for `package.transfer` and `(event, package_id)` for the others: a retry carries the same body, the same `timestamp` and the same signature.

#### `package.transfer`

A transfer from the address was paid from a package. Sent once **per package** the transfer was charged to — almost always one event per transfer; a transfer that took the last transfer of one package and continued on the next produces one event for each.

<ResponseField name="tx_hash" type="string">
  The transfer transaction on chain.
</ResponseField>

<ResponseField name="units" type="number">
  Transfers taken from **this** package for this transaction. A transfer to an address that holds no USDT needs double energy and counts as `2`, which can be split across two packages.
</ResponseField>

Here `status` is `completed` when this transfer used up the package.

```json Response
{
  "event": "package.transfer",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 312,
    "tx_hash": "9f8e7d6c5b4a...",
    "units": 1
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.completed`

The package stopped serving transfers.

<ResponseField name="reason" type="string">
  `transfer` — a transfer used up the package; `subscription` — the daily charge used it up; `manual` — support closed the package. After `manual`, `remaining` can be above zero, but those transfers can no longer be used.
</ResponseField>

<ResponseField name="tx_hash" type="string | null">
  For `reason: "transfer"`, the transfer that closed the package; `null` otherwise.
</ResponseField>

A package with nothing left — for example a regular one-transfer package, whose first daily charge took its only transfer — is closed by the next transfer without a `package.transfer` of its own: you receive only `package.completed` with that transfer's `tx_hash`.

```json Response
{
  "event": "package.completed",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "completed",
    "quota_total": 500,
    "remaining": 0,
    "reason": "transfer",
    "tx_hash": "9f8e7d6c5b4a..."
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.activated`

The package became active and its transfers get energy from now on. Sent for every activation — including a purchase from balance, whose response already says `active`, and an invoice payment, which activates the package shortly after the payment is seen on chain.

<ResponseField name="payment_method" type="string">
  How the package was paid: exactly `balance`, `TRX` or `USDT`.
</ResponseField>

```json Response
{
  "event": "package.activated",
  "data": {
    "package_id": 318,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "active",
    "quota_total": 500,
    "remaining": 499,
    "payment_method": "USDT"
  },
  "timestamp": "2026-10-15T14:51:16.986341+00:00"
}
```

#### `package.expired`

An invoice for a package was not paid within its 30-minute window. Nothing was charged; buy again to get a new invoice. No extra fields; `remaining` equals `quota_total` and is not available to use.

```json Response
{
  "event": "package.expired",
  "data": {
    "package_id": 319,
    "address": "TXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX",
    "status": "expired",
    "quota_total": 500,
    "remaining": 500
  },
  "timestamp": "2026-10-15T15:21:16.986341+00:00"
}
```

### Delivery

- Up to **3 attempts**, with pauses of **1 second** and then **4 seconds** between them. There is no pause after a success and none after the last attempt.
- **10 seconds** timeout per attempt.
- We expect any **`2xx`**. Anything else counts as a failed attempt.
- **Redirects are not followed.** A `301`/`302` is a failed attempt, not a hop.
- Missed events are **not** backfilled. When all three attempts fail, that event is gone; reconcile with [Get Order](/api-reference/orders/get-order), [Get Invoice](/api-reference/invoices/get-invoice) or [List Packages](/api-reference/transfer-packages/list) rather than waiting for a replay.
- **Events are not ordered.** Each one is delivered on its own, so a later event can arrive first. A retry carries the same body, the same `timestamp` and the same signature.
- Every order of the account sends events, auto-refill included, so a busy account gets many of them. Answer `2xx` at once and do the heavy work after the response.

Your URL must resolve to a **public** address. Loopback, private and link-local ranges are rejected, and so is a host that does not resolve — in both cases nothing is sent and no log row is written.

### Verifying the signature

Every request carries `X-Webhook-Signature: sha256=<hex>`, an HMAC-SHA256 over the **raw request body** keyed with your webhook secret.

Two details decide whether your check works:

1. **Strip the `sha256=` prefix** before comparing. The header is not a bare hex digest.
2. **Hash the bytes you received**, not a re-serialized object. Parsing the JSON and dumping it again changes key order and spacing, and the signature will never match.

Your signing secret is shown in [Dashboard → API](https://tronrental.com/dashboard/api) next to the webhook URL. It is not returned to API-key requests — reading it requires signing in on the website.

<CodeGroup>
```python Python
import hashlib
import hmac

def verify_webhook(raw_body: bytes, signature_header: str, secret: str) -> bool:
    prefix, _, received = signature_header.partition("=")
    if prefix != "sha256" or not received:
        return False
    expected = hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, received)

# In your handler — pass the RAW body, before any JSON parsing:
#   verify_webhook(request.body, request.headers["X-Webhook-Signature"], secret)
```

```javascript JavaScript
const crypto = require("crypto");

function verifyWebhook(rawBody, signatureHeader, secret) {
  const [prefix, received] = String(signatureHeader).split("=");
  if (prefix !== "sha256" || !received) return false;
  const expected = crypto.createHmac("sha256", secret).update(rawBody).digest("hex");
  const a = Buffer.from(expected);
  const b = Buffer.from(received);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

// In Express, capture the raw body first:
//   app.use(express.json({ verify: (req, _res, buf) => { req.rawBody = buf; } }));
```
</CodeGroup>

<Warning>
  Verify the signature before acting on the payload, and compare in constant time (`hmac.compare_digest` / `crypto.timingSafeEqual`). Comparing with `==` leaks timing.
</Warning>
